# n8n setup

Six workflows. All are generated by `npm run build:n8n` from `email/copy/campaign.json`,
so never hand edit the JSON: edit the deck and regenerate. `npm run n8n:sdk` converts that
JSON into n8n Workflow SDK code, which is what the n8n API accepts.

```
01-intake.json        DMS repair order feed  ->  eligibility  ->  enrollment row
02-scheduler.json     hourly  ->  claim whatever is due  ->  send  ->  advance state
03-events.json        purchase / unsubscribe / bounce  ->  exit and suppress
04-error-handler.json any failure in any of the above  ->  Slack alert
05-pricing.json       hourly  ->  price unpriced enrolments via the rating API
06-bounce-watcher     IMAP    ->  read bounces back out of the sending mailbox
```

## Sending over SMTP

The campaign sends from the dealership's own warmed mailbox rather than through an ESP.
That keeps the From address and the domain reputation with the dealer, and it costs two
things that are worth knowing about because both are compensated for rather than ignored.

**No provider webhooks.** Bounces and complaints arrive as ordinary mail in the sending
mailbox instead of as events. Left alone the campaign would keep mailing dead addresses for
60 days, which is how a warmed domain stops being warm. Workflow 06 reads them back over
IMAP and posts to the same exit endpoint an ESP webhook would have hit.

It matches on the RFC 3463 status class rather than on wording, because delivery status
notifications are not standardised in practice. Hard failures (5.x.x, user unknown, address
rejected) suppress. Soft failures (4.x.x, over quota) deliberately do **not**, since a full
mailbox is not a dead customer. Abuse reports suppress as complaints. Ordinary replies and
out-of-office messages are ignored, which matters: a customer replying to ask a question
must never be suppressed for it.

**No one-click `List-Unsubscribe` header**, because n8n's SMTP node cannot set custom
headers. At 200 a day you are well under Google's 5,000-a-day bulk sender threshold where
that header becomes mandatory, so this is a best-practice gap rather than a compliance one.
The unsubscribe link in the footer is set larger and bolder than the surrounding legal text
to compensate: a reader who cannot find it presses Report spam instead, which costs the
domain far more.

Set `appendAttribution: false` stays on the send node. Without it n8n adds its own footer to
every message, which would put "sent automatically with n8n" under a dealership's customer
email.

## Why this is not one long Wait node chain

A 60 day drip built on Wait nodes is the obvious way to do this and it is a trap. Wait
nodes hold execution state in the n8n instance. Restart n8n, upgrade it, redeploy it or
lose the container, and every contact mid-flight is gone silently. You also cannot query
"who is on step 6," cannot pause one contact, and cannot change cadence for people
already enrolled.

This uses a durable state machine instead. The enrollment row in Postgres is the truth.
n8n is stateless and disposable. You can destroy and rebuild the n8n instance mid
campaign and nothing is lost.

Concretely that buys you:

- **Restart safety.** State lives in the database, not in an execution.
- **No double sends.** The scheduler claims rows with a single atomic `update ...
  returning` using `for update skip locked`, and leases them two hours forward. Two
  schedulers racing cannot pick the same row. A crashed run retries in two hours instead
  of stranding the contact or sending twice. `vsc_send_log` has a `(enrollment_id, step)`
  unique constraint as a second line of defence.
- **Late sends do not compress the cadence.** Each next send is computed from the
  enrollment date, not from "now," so an outage delays one email rather than bunching the
  remaining nine.
- **Exits are immediate.** Suppression is re-checked inside the claim query, not only at
  intake. Someone who unsubscribes on day 11 of 60 gets nothing further, with no sweep
  job needed.
- **Quiet hours are free.** Outside the 09:00 to 19:00 dealer local window the prepare
  step emits nothing, the lease expires, and the row is naturally retried in the next
  window.
- **Adding dealership two is a copy.** Every workflow is parameterized on `dealer_id`.

## Remaining setup

**1. Credentials.** All four are attached. Confirm each points where you expect.

| Credential | Type | Used by | Status |
|---|---|---|---|
| Postgres account | Postgres | 01, 02, 03, 05 | attached |
| SMTP account | SMTP | 02 send | attached |
| IMAP account | IMAP | 06 bounce watcher | attached |
| Header Auth account | Header Auth | 03 events webhook | attached, but shared with other workflows. Give the campaign its own secret. |

**2. Variables, not environment variables.** n8n Cloud blocks environment variables
outright. An expression reading `$env` there does not come back empty, it comes back with
the string `access to env vars denied`, which would have put that text into the From
address of every send and into the rating API key header on every price. Every workflow
reads `$vars` instead. Confirmed by probe on this instance: `$env` denied, `$vars`
available.

Set these in n8n under **Settings, Variables**:

| Variable | Value | Notes |
|---|---|---|
| `SEND_FROM` | `Bob Johnson Dodge Jeep Ram <northcountryrecalls@bobjohnsonauto.com>` | The dealership address Resend signs as. The domain must be verified in Resend first. |
| `SEND_REPLY_TO` | `northcountryrecalls@bobjohnsonauto.com` | Monitored. Replies must reach a person. |
| `UNSUBSCRIBE_URL_BASE` | `https://bbvkqwcapqsytrdrubci.supabase.co/functions/v1/vsc-unsubscribe` | Already deployed. |
| `PREFERENCES_URL_BASE` | same as above | Points at the same function today. |
| `CAMPAIGN_EVENT_URL` | `https://ryan-3522-williams.app.n8n.cloud/webhook/vsc/events/bob-johnson` | The internal event endpoint, for DriveOne checkout and CRM exits. Header authenticated. |
| `DRY_RUN` | *(an email address, or unset)* | Set it and every send in the run is redirected there with the intended recipient in the subject, and no state is written. Unset for live. A forgotten value sends the whole campaign to one inbox with nothing looking wrong. |
| `RESEND_WEBHOOK_SECRET` | *(the `whsec_...` signing secret from the Resend webhook)* | Workflow 03 verifies every Resend delivery against it and refuses the request if it is unset. |
| `RATING_API_KEY` | *(the captured API key)* | Sent as the `x-captured-api-key` header. Workflow 05. |
| `SLACK_ALERT_WEBHOOK` | *(the Slack incoming webhook)* | Workflow 04. Without it, failures are silent. |

`QUOTE_API_BASE` is optional: workflow 05 falls back to
`https://www.getelevatewarranty.com/api/partners` when it is unset.

Variables are stored in plaintext in n8n settings. `RATING_API_KEY` would be better as a
Header Auth credential, which n8n encrypts at rest; the trade is one dropdown on the Get
Quote node against a key sitting readable in Settings. Worth doing before this runs for a
second dealership.

Templates are read out of Postgres now, so there is no `TEMPLATE_BASE_URL`, no hosting to
stand up, and no deployment-protection bypass. Quote links come from the rating API
response rather than being built locally, so there is no `QUOTE_URL_BASE` either.

## Blocker: the Code node task runner

Two production executions of a two-node probe on this instance failed identically after
exactly 60 seconds:

```
Task request timed out
Your Code node task was not matched to a runner within the timeout period
(waited 60 seconds). This indicates that the task runner is currently down,
or not ready, or at capacity.
```

Nothing in this repo can fix that: it is the instance's own Code execution service.
Workflows 02, 03, 05 and 06 all depend on Code nodes, so while this persists the campaign
cannot enroll, price, send, or process a bounce. A Set-node-only probe on the same
instance ran fine in 77 ms, which is what proves the fault is specific to the Code runner
rather than to executions generally.

Check it before activating anything: run any workflow with a Code node and confirm it
finishes. If it still times out, that is an n8n Cloud support question.

## Throughput and timing

Set in `brand/dealers/<id>.json` under `sending`, and compiled into workflow 02.

| Setting | Value | Why |
|---|---|---|
| `dailyCap` | 200 | Hard ceiling per dealer-local calendar day. |
| `days` | Tue, Wed, Thu | Monday inboxes get cleared in bulk, Friday afternoon decays. |
| `hours` | 9, 10, 11, 13, 14, 15, 16 | Mid morning and early afternoon, skipping lunch. |
| `maxPerRun` | 45 | Stops a backlog arriving as one spike. |

`Send Window Gate` runs before the claim, so an out-of-window hour costs one cheap check
rather than a wasted database lease. It spreads whatever is left for the day across the
hours still to come, so the queue drains smoothly instead of firing at the top of the window.

The cap is enforced **inside the claim statement**, as a `least(per_run, cap - sent_today)`
limit, so two scheduler runs racing cannot jointly exceed it. Anything unsent when the
window closes simply waits: because each next send is computed from the enrolment date
rather than from the last send, slipping a day never compresses the rest of the sequence.

At 432 enrolled across ten steps that is 4,320 sends, about 8 weeks at 600 a week.

The day boundary is derived from the timezone rather than a fixed offset, so it follows
daylight saving. Verified: the boundary moves from 04:00Z to 05:00Z when EDT ends.

These are starting heuristics, not measured truths. Supabase already records
`last_email_opened_at` and `email_open_count`, so tune the days and hours against real opens
once a few thousand sends have landed.

## Where the templates live

In Postgres, in `vsc_email_template`, read by workflow 02 over the connection it already
holds. They used to be fetched over HTTPS from Vercel, which needed public hosting, a
deployment-protection carve-out and a base URL in config, and it added a failure mode: a
template that could not be fetched meant a failed send. A row in the same database has
none of those properties.

Publishing is a build step, not a deploy:

```bash
npm run build                                       # render email/dist/*.html
node scripts/publish-templates.mjs bob-johnson 1 2  # emit SQL for steps 1 and 2
```

The whole set is about 200 KB of SQL, which is more than some clients will take in one
statement, so it takes a step range and goes up in slices. Apply the SQL with the Supabase
MCP, `psql`, or the dashboard.

**Verify every publish.** A template that is subtly wrong reaches customers. After
applying, compare each row against the file it came from:

```sql
select step, slug, md5(html), length(html)
from vsc_email_template
where dealer_id = 'bob-johnson' and campaign_id = 'bj_postro_vsc_2026'
order by step;
```

```bash
md5sum email/dist/*.html
```

The two lists must match exactly. `publish-templates.mjs` inserts the file verbatim, so
any difference is a transport problem, not a rendering one.

The Vercel project still builds the review gallery and the filled sample previews for
client sign-off. Nothing at send time depends on it.

## Adding a second DMS

Edit one node: `Normalize RO Payload` in workflow 01. Add a block to `MAPPINGS` keyed by
vendor and set `DMS_VENDOR`. Blocks inherit nothing from each other, so a wrong key in
one vendor can never break another. No other node reads raw DMS fields.

## Adding a second dealership

1. Copy `brand/dealers/bob-johnson.json` to `brand/dealers/<new>.json` and fill it in.
2. `node email/build.mjs <new>`
3. `node n8n/build-workflows.mjs` (point it at the new dealer file)
4. Import the four workflows under a new `dealer:<new>` tag.

Enrollment rows are keyed by `dealer_id`, so dealerships share the database without
touching each other.

## Changing the cadence

Edit `sendDay` in `email/copy/campaign.json`, run `npm run build`, re-import workflow 02.
The schedule is compiled into the workflow from the deck, which is the whole reason the
workflows are generated rather than hand built. Contacts already enrolled pick up the new
cadence on their next step, because the next send time is computed at send time rather
than at enrollment.

## Keeping the repo and the instance in sync

`npm run build:n8n` writes `n8n/workflows/*.json`. `node scripts/to-n8n-sdk.mjs
n8n/workflows/<name>.json` converts one of those into SDK code, which is what the n8n API
takes. The converter carries SQL and Code node bodies across verbatim rather than retyping
them, so what runs in n8n is what was verified against the database.

To check for drift, regenerate and compare against the live workflow. The only expected
difference today is the `id` on a filter condition inside the two IF nodes (workflows 02
and 03): those were created before condition ids were made deterministic, so the live
values are random and the generated ones are hashes. The id is an internal key with no
behaviour attached, and it aligns the next time either workflow is updated from the repo.
